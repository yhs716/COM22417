DB 비밀번호를 잊었을 때 · DBA 조회와 재설정

Oracle은 DB 인증에 비밀번호의 단방향 해시를 사용하므로 DBA 권한으로 기존 비밀번호 원문을 조회·복호화하는 기능은 제공하지 않습니다. DBA_USERS의 PASSWORD_VERSIONS는 해시 종류를 나타내며 비밀번호 원문이 아닙니다.

  1. 본인의 발급 기록이나 본인이 관리하는 Render Environment의 DB_PASSWORD, 개인 로컬 security/student.env에 저장한 값을 확인합니다. 저장된 값이 DB에서 변경한 최신 암호와 일치하는지는 실제 접속으로 확인해야 합니다.
  2. 확인할 수 없으면 담당 관리자에게 새 암호 발급을 요청합니다. Autonomous Database의 ADMIN은 ALTER USER로 사용자 암호를 재설정할 수 있습니다. 이는 기존 암호를 알아내는 기능이 아닙니다.
  3. 암호가 재설정되면 본인 Render의 DB_PASSWORD도 새 값으로 맞추고 환경변수를 배포에 적용한 뒤 연결 테스트·로그인을 다시 확인합니다. 로컬에서 쓰는 개인 설정도 함께 확인합니다. Wallet 암호는 DB 사용자 암호와 별개입니다.

DBA 권한이 있어도 DB에 저장된 인증 정보와 별도로 보관한 암호 기록은 구분해야 합니다. 평가용 DB 계정·암호는 LMS 과제 제출란으로 담당자에게 제공하며 안내서·Git·공개 게시글에는 올리지 않습니다. Oracle 비밀번호 인증 원리 · Autonomous Database 사용자 암호 변경

미션을 바꿀 때 · 선택과 DB 적용을 구분하세요

미션 선택은 SQL 가이드·CSV의 대상을 바꿉니다. DB 객체·데이터·모델은 그대로입니다. 화면 상단에서 선택 미션 / DB 규약 확인 / 마지막 전처리·모델 연계를 함께 확인하세요.

  1. 기존 미션을 계속할 때: ‘DB 미션으로 돌아가기’로 같은 미션을 선택합니다. DB 지문이 같으면 기존 연계 기록을 사용합니다.
  2. 새 미션을 적용할 때: 필요한 기존 작업을 먼저 보관하고 선택 미션의 DATA → PREPARED → PREDICT → RUN을 SQL Developer에서 직접 적용하세요. 제공 테이블 재생성 SQL은 기존 행을 삭제하므로 실행 범위를 확인하세요.
  3. 웹을 새로고침해 객체 준비를 확인하고 선택 미션의 CSV를 적재합니다. 전처리·RAW/CLEAN 학습을 직접 수행한 뒤 해당 단계에서 SQL 실행 결과 연계를 누르고 TEST 평가·예측을 진행합니다.

서버는 세 테이블의 컬럼·자료형·필수값과 RUN의 컴파일·입출력 규약·소스를 검사합니다. 미션 불일치·적용 중이면 이전 성공을 새 미션에 표시하지 않고 연계·평가·예측을 차단합니다. 객체 준비는 현재 규약이 맞으면 조회만으로 완료됩니다. 전처리·모델은 현재 객체 지문에 대한 연계가 없으면 미완료이며 평가·예측을 차단합니다. CSV는 적재 대상 한 테이블만 맞으면 준비 도중에도 적재할 수 있습니다. 기존 객체는 자동 변경하지 않습니다.

초기화 후 표시: 미션의 DATA·PREPARED·PREDICT·RUN이 모두 없으면 생성 전 상태이며 상단 불일치 경고를 숨깁니다. 일부 객체만 남거나 선택 미션과 다르면 주황색 경고를 유지합니다. SQL Developer에서 삭제한 뒤에는 화면의 새로고침으로 DB 상태를 다시 확인하세요. 기본과제 객체만 삭제한 경우 미션 객체는 그대로입니다. 마지막 연계 기록만으로 성공 처리하지 않습니다.

객체·프로시저 입출력 규약 상세 보기

CSV·정제·재학습에서 지킬 규칙
  • CSV는 UTF-8(또는 BOM), 첫 줄 영문 헤더, 쉼표 구분입니다. 세 과제 모두 웹 업로드는 파일당 2 MiB·5,000행까지입니다. 대상 테이블을 먼저 만들고 실제 컬럼 이름과 맞추세요.
  • CSV 교체 적재는 대상 테이블의 기존 행을 교체합니다. 파일 선택만으로 DB는 바뀌지 않습니다. 화면 확인 메시지에서 대상·범위를 확인하세요. 적재는 한 개의 바인드 INSERT를 500행씩 묶어 처리합니다.
  • 미션 CSV는 학습·TEST 1,500행(TRAIN 1,200 / TEST 300), 예측 30행입니다. 합성 데이터의 설명변수는 0~100 지수입니다. 빈 값·unknown·999999 등 결함을 점검하고 TEST와 정답은 성능을 높이려고 바꾸지 마세요.
  • 원본·프로시저를 바꾸면 전처리 저장 → 전체 다시 학습 → 연계(미션·창의) → TEST 재평가 순서입니다. 전체 다시 학습은 기존 모델을 지우고 현재 TRAIN 전체로 다시 만듭니다.
  • PREPARED의 준비값·FIT_YN만 수동 수정했다면 COMMIT 후 재학습합니다. PREPARE를 다시 실행하면 수동 수정한 준비값이 교체됩니다.
  • 처음 상태로 되돌릴 때는 데이터 비우기·전처리값 비우기·모델 삭제·확정 해제·오브젝트 삭제 중 필요한 범위만 선택합니다. 미션은 관련 SQL 가이드, 창의는 직접 작성한 SQL로 수행합니다.
코딩도움말과 예측 결과 읽기

화면 → 이벤트 → API → 서비스 → DB 연결 → 실행 SQL 순서로 실제 파일을 추적합니다. 왼쪽 파일·구간을 선택하면 오른쪽 파일 전체에서 해당 위치로 이동합니다.

미션·창의의 직접 수행 버튼은 준비 상태에 따라 활성화되며 실행 SQL 첫 항목을 엽니다. 구문을 복사해 발급 계정의 SQL Developer에서 F5 실행 후 SQL 실행 결과 연계를 누르세요. ?는 화면 FLOW부터 엽니다. 창의는 본인 RUN 호출·고정 객체 정리만 제공하며 구현 답안은 제공하지 않습니다.

기본·미션의 실행 SQL에는 원본과 현재 선택값을 적용한 실행용 런타임 SQL이 함께 나옵니다. 생성 미리보기와 성공한 실제 조회 기록을 구분하며 도움말을 열어도 DB 작업은 실행되지 않습니다.

식별키는 파랑, 설명변수는 초록, 타깃은 보라, 기타는 회색입니다. 색과 역할 배지를 함께 읽으세요. 예측은 학습과 같은 특성 이름·의미·단위·전처리를 사용합니다.

예측 입력과 PREPARED 값은 DB에 저장됩니다. 기본·제공 미션 프로시저의 분류·확률은 조회 결과이고 화면 기록은 새로고침하면 지워집니다. 성공 요약의 DB 저장·이관은 아래 ‘진행 상태 공유’를 확인하세요. 창의 프로시저의 별도 결과 저장은 본인이 구현한 SQL에 따릅니다.

저장·적재 중에는 진행바가 표시됩니다. 정상 완료 알림은 잠시 뒤 사라지며 오류와 확인 레이어는 직접 확인합니다. 문의 시 오류 코드·실행 작업을 전달하고 비밀번호·Wallet은 보내지 마세요.

진행 상태 공유 — 로컬·Render가 같은 Oracle 기록 사용

진행 검증 기록과 미션 선택은 발급 계정의 Oracle DB에 저장됩니다. 로컬과 Render에서 같은 DB·발급 계정·미션을 사용하면 같은 기록과 현재 데이터를 대조합니다. 세 과제의 성공 기준과 작업번호는 유지됩니다.

항목저장 위치·동작
원본·전처리·RUN·모델기존 Oracle 실습 객체. 데이터·프로시저·모델 변경을 현재 지문과 대조
전처리 확인·모델 최신성·선택 모델·평가/예측 성공 요약같은 계정의 OML_WEB_STATE 관리 테이블. 해시·생성 시각·건수 등 검증 메타데이터만 저장
미션 선택같은 관리 테이블에 학번별로 저장. 재접속·배포 후 DB에서 복원
로그인·조회 화면쿠키·세션은 인증용. 조회 표·선택 파일·열린 탭은 화면 상태이며 성공 저장소가 아님

새 버전으로 로그인하면 발급 계정을 인증한 뒤 없는 관리 테이블만 준비합니다. 기존 실습 테이블·행·모델은 삭제하거나 재학습하지 않습니다. 연결 테스트는 저장소를 만들지 않습니다. DB 저장 실패 시 로컬 파일의 성공 표시로 대체하지 않습니다.

이전 버전에서 수행한 기록이 있는 경우: 기존 로컬 소스와 runtime 파일을 보존하고, Render에 새 버전을 배포하기 전에 로컬의 활성화된 가상환경에서 아래 명령을 한 번 실행하세요. STUDENT00은 본인 발급 DB 계정으로 바꿉니다.

python -m backend.progress_store --owner STUDENT00 --student-id 본인학번

DB에 해당 기록이 없을 때만 기존 model-choice·mission-selection JSON을 이관합니다. 이미 DB에 저장된 기록은 덮어쓰지 않으며 이후 JSON은 진행 판정에 사용하지 않습니다. 기존 파일을 Git·학생 ZIP에 넣지 마세요. 처음 사용하는 학생은 새 버전으로 바로 로그인하면 됩니다.

로컬과 Render 모두 새 버전을 적용하고 다시 로그인한 뒤 최종 현황 확인을 누르세요. Python 변경은 실행 중 프로세스에 자동 적용되지 않으므로 기존 로컬 서비스는 한 번 재시작해야 합니다. 재시작 시 로그인은 종료되지만 DB 진행 기록은 남습니다.

서로 다른 환경이 동시에 같은 기록을 변경하면 이전 버전의 저장을 거부합니다. 안내가 나오면 현황을 다시 조회한 뒤 실행하세요. 관리 기록의 COMMIT은 실습 데이터의 미완료 트랜잭션과 분리됩니다. 원본·프로시저·모델·예측 입력 변경으로 기준이 맞지 않으면 양쪽 모두 다시 대기로 판정합니다.

관리 테이블은 채점용 임의 점수나 정확도 합격선을 만들지 않습니다. 비밀번호·Wallet·CSV 원문도 저장하지 않습니다. 기존 4단계·기본 19개 세부 기준과 실제 평가·예측 성공 검증을 유지합니다.

확인한 원인: WALLET_DIR=/etc/secrets는 설정했지만 Secret Files에 Wallet 파일이 없었습니다. 로컬은 ZIP에서 Wallet을 읽어 접속할 수 있었지만 Render는 지정된 폴더의 파일을 찾지 못했습니다. 폴더 경로를 입력하는 것만으로 Wallet이 업로드되거나 로컬 파일이 복사되지는 않습니다.

  1. 같은 원본 Wallet 준비: 학생 ZIP의 security/Wallet_PCUORA.zip을 임시 폴더에 풉니다. 서로 다른 Wallet의 파일을 섞지 않습니다.
  2. Secret Files 등록: Render → 해당 Web Service → Environment → Secret Files → Add Secret File. Filename에 tnsnames.ora, Contents에 해당 파일의 전체 원문을 붙입니다. 같은 방법으로 ewallet.pem도 등록합니다. ZIP 파일 자체나 파일 경로를 Contents에 넣지 않습니다. PEM의 BEGIN/END 줄과 중간 줄바꿈을 보존합니다.
  3. 경로·값 확인: WALLET_DIR는 /etc/secrets 폴더이며 ZIP 경로나 파일 경로가 아닙니다. 앱이 읽는 파일은 /etc/secrets/tnsnames.ora와 /etc/secrets/ewallet.pem입니다. WALLET_DIR가 있으면 WALLET_ZIP보다 우선합니다. WALLET_PASSWORD는 배포한 압축소스의 security/student.env 값을 사용하고 ORACLE_CLIENT_LIB는 빈 값으로 Thin 연결을 사용합니다.
  4. 저장과 적용: Secret Files의 Save Changes가 시작한 자동 배포가 Live가 될 때까지 기다립니다. Wallet 파일만 추가한 경우 Git 수정·push나 별도의 수동 배포를 다시 할 필요가 없습니다. 환경변수를 Save only로 저장했다면 다음 배포 전까지 실행 중 서비스의 값은 바뀌지 않습니다.
  5. DB 연결 재검사: Render 메인에서 학번·이름·본인의 DB 비밀번호 → DB 연결 테스트 → 로그인 순서로 확인합니다. DB 비밀번호가 서버 설정과 다르면 ‘DB 비밀번호가 일치하지 않습니다’가 나오며 DB 접속을 시도하지 않습니다. 일치하더라도 Wallet·서비스·네트워크·실제 DB 인증이 실패하면 로그인되지 않습니다. /healthz의 정상 응답만으로 DB 접속 성공을 판단하지 않습니다.

DB-CONNECTION 해석: 이번 파일 누락은 Oracle 접속 전 파일 읽기 단계에서 발생하여 ORA-/DPY- 코드 없이 공통 DB-CONNECTION으로 표시됐습니다. 네트워크 장애로 단정하지 말고 위 파일 목록부터 확인하세요. Render 화면에 나온 student.env 안내는 공통 로컬용 문구이며 Render에서는 Environment와 Secret Files를 확인합니다. 두 파일이 있는데도 실패하면 DB_DSN·Wallet 암호·원본 파일 일치·DB 사용 상태를 순서대로 확인하세요.

  2. 표시된 HTTPS 주소의 /healthz를 열어 {"status":"ok"}를 확인합니다. 이는 웹 프로세스 응답이며 DB 연결 성공을 뜻하지 않습니다.
